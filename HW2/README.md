Problem 1: 
The primary advantage of utilizing a tail pointer in a linked list is that the time it takes to append a node at the end of a list is a constant O(1). You do not need to walk through the whole list to get to the last value, which would be O(n) for a linked list of n length. This tail pointer also provides easy access to the end of the list, which can be utilized for many different directives and helper functions in our program and driver.

Problem 2:
The singly linked list is a chain of nodes, where each node contains a reference to the value and the next node. The list contains a head, tail, and a length/count reference. The list will be initialized to have no head, tail, or length until elements are added to the list.

Operations:
Append - This operation is optimized at O(1) since the tail pointer lets us add directly after the last node. This is better than jumping through each node with a O(n). The count increases by 1.
Prepend - Also optimized at O(1) since we simply point the new node at head, then move the original head. The count increases by 1.
Insert - This method utilizes Append if the index indicated would essentially be the same as adding to the end of the list, and Prepend when we want to insert the value at the beginning of the list (index = 0). For the case ins which we add in the middle of the list, we must point to the node before the target inde. We will make that node point to our new node. Then we will make the new node point to the remainder of the list to complete the list. the count increases by 1. This operation uses a helper function that I will discuss shortly.
Get - this operation walks through the list until it finds the given index, where O(i). This operation uses a helper function that I will discuss shortly.
Find and Delete - These operations are a linear scan O(n) through the list. Find traverses through the list and keeps track of each iteration until it finds the target value, then returns that index. Delete also traverses through the list node by node until it finds the target value. Delete utilizes a helper function that I will discuss shortly.  
Delete_at - This operation walks through the list a total of I times. It identifies the node before the target index then uses an unlinking helper function to remove the node and connect the two adjacent pieces (similar to delete). I will discuss the helper function shortly.
Len - This operation simply returns the count of the list, so O(1). 
Print_list - This operation traverses through each node so O(n). It adds the values of the singly linked list into a list [] as strings, and then prints them one by one, joined by "->" in between each node.

There were a handful of helper operations that I created to perform certain actions that I noticed multiple functions needed: _check_index, _node_at, and _unlink. I created these helper functions for simplicity and practical reasons. Utilizing s helper function prevents me from repeating the same code over and over. Additionally, utilizing a helper function allows me to de-bug and alter my code quickly. The helper function allows for flexibility if I wanted to alter the way a certain function behaves. Instead of changing the same thing multiple times if I need to make an edit or fix a bug, I simply need to fix/edit the helper function that all functions call to.

_check_index(index) - very simply, this helper function raises an IndexError if the index given is out of range. The insert, get, update, and delete_at functions utilize this helper function to confirm that the index given is a valid index to use for the directive.
_node_at(index) - very simply, this helper function returns the node at a desired index. it traverses through the list i times and the last node it arrives at is returned (at position = index). The get, update, and delete_at functions utilize this helper function to optimize.
_unlink(prev, current) - this helper function takes as inputs the two nodes in which you want to unlink. the prev node will remain in the list but the current node will be removed. The prev node will now point to the node that originally followed current. The delete and delete_at functions use this helper function.

I decided to store length as a variable that we can call for the _len_ function. The alternative is counting through the list entirely each time you want to know the total number of nodes in the list. In exchange for a little bit of memory, I save a lot of time to call the _len_ function.

For the driver, we use "for line in sys.stdin" to read the text one line at a time so that memory does not grow. If we read the whole text first, we would use more memory with no extra benefit.

For text validation, the driver first checks for blank lines or comments. it skips these lines. Once it finds usable text, it confirms whether the directive is valid. Next, it confirms that the correct number of arguments is provided following the directive. Each directive has a specified number of arguments that it should be paired with. Next, the driver confirms that the argument provided is a whole number. Indices must be whole numbers, and we will assume that values can only be whole numbers for now. Finally, the driver will run the directive/operation on the list. 

I created a dictionary that stores the directives as keys and the expected number of arguments as the values. The dictionary helps to confirm that the given directive can be followed appropriately and has the correct number of expected arguments. Additionally, the dictionary is the source of known directives to search through for validation.

WHOLE_NUMBER is a pattern matcher that checks and confirms whole numbers are being input as arguments for the indices or values.

I created a DirectiveError class so that exceptions would interrupt the code altogether, print a warning then continue to the next line. This also allows for practical usage while I am coding. If I encounter an issue with a directive that is unknown, it will be printed to me so that I can address. If I used a built-in like ValueError, it crashes loudly and will not be hidden as a warning. A blanket Exception would simply swallow it.

I created functions called parse_index(token) and parse_value(token). Parse_index simply confirms that the argument passed through is a whole number or it raises an error. Additionally it returns the confirmed whole number as an integer. This function is called in the executive of any directives that utilize an index as an argument. Parse_value also confirms that the arguments is a whole number and then returns as an integer. If the argument is not a whole number, it remains as a string.

I also created a warn function for troubleshooting purposes. This function prints the line number of any errors and the corresponding message. This function is utilized anytime there is an IndexError, or DirectiveError.

Problem 4:

My program stores a sorted list of numbers in a doubly linked list. Each node holds a value along with a reference to the node before it and the node after it. The list keeps track of the first node (the head), the last node (the tail), and a count of how many nodes there are. The idea that everything else depends on is that the list is always in ascending order. The user never chooses where a value goes because the only way to put a value in is the add method, and add always places it in its correct sorted position. Since every other method can trust that the list is sorted, they can take shortcuts that an unsorted list would not allow.

To add a value, I first walk down the list from the head, moving forward as long as the current node's value is less than or equal to the new value. This stops at the first node that is strictly larger than the new value, or at the end of the list if there is no node. Because the walk keeps going past equal values, a duplicate ends up after the copies that were already there. Then I connect the new node in one of two ways. If I ran off the end, the new node becomes the new tail, and its previous reference points to the old tail. If the list was empty, it also becomes the head. Otherwise, I insert the new node just before the larger node I stopped at. I set the new node's own references first, so that it points to the larger node and to that node's old predecessor. Then I update the neighbors, so the old predecessor now points forward to the new node, or the new node becomes the head if there was no predecessor, and the larger node's previous reference now points back to the new node. Setting the new node's references before touching the neighbors means I never lose track of part of the list in the middle of the change. In both cases I add one to the size.

To delete a value, I first search for the first node that holds it. The search is a recursive helper that looks at one node and then calls itself on the next node. It stops and reports "not found" if it reaches the end of the list, and it also stops if it reaches a node whose value is bigger than the one I'm looking for, because in a sorted list the value cannot appear any later. If it finds a match, it returns that node. If no node was found, delete returns False. Otherwise I remove the node by connecting its two neighbors to each other. If the node has a previous node, that node's next reference skips over it. If it doesn't, the node was the head, so the head moves forward. The same logic applies on the other side, so if the node has no next node, it was the tail and the tail moves backward. These two checks make deleting the first node, the last node, a middle node, and the only node in the list all work, and in the last case both head and tail become empty. Then I subtract one from the size and return True. Only the first matching node is removed, so deleting a value that appears twice removes just one copy.

The exists and count methods use the same kind of recursive helper. For exists, the helper stops with a negative answer at the end of the list or as soon as the current value is bigger than the target, and it stops with a positive answer when it finds a match. For count, the stopping rules are the same, but at each node it adds one if the node matches and zero if not, then adds the count from the rest of the list. In a sorted list, all copies of a value sit next to each other, so count does not need to stop at the first match, and it simply keeps going through the run of duplicates until it hits a larger value. The total method works the same way, except that it has no shortcut. Each call returns the current node's value plus the total of everything after it, and an empty remainder contributes zero, so it always visits every node. The print_list method does the same kind of thing with strings. If the list is empty it prints the text "(empty)". Otherwise, the helper returns the current value, followed by an arrow, followed by the string for the rest of the list, with the last node returning just its own value, and the finished string is built as the recursion unwinds.

The sum_middle_three method uses the stored size, called n, so it does not have to count the nodes. If n is less than 3 it raises a ValueError. Otherwise it computes mid as n divided by 2, rounded down. For an odd n, the three middle nodes are at positions mid minus 1, mid, and mid plus 1. For an even n, there is no single center, so following the assignment, I use positions mid minus 2, mid minus 1, and mid. In both cases I work out the starting position, walk that many steps from the head, and add the value at that node and the two after it. The median method works similarly. If the list is empty it raises a ValueError. For an odd n it walks to position mid and returns that value, and for an even n it walks to position mid minus 1 and returns the average of that node's value and the next one, which is why even-length lists give a decimal result such as 9.0.

The driver program reads standard input one line at a time, so it never loads the whole file into memory. It strips each line, skips lines that are blank or start with a pound sign, and splits the rest into a directive and its arguments. Then it checks that the directive is one it knows and that it has the right number of arguments, using a small dictionary that maps each directive to its argument count. If the argument is a number, it tries to convert it to an integer first and then to a decimal, and it rejects values like nan and inf, because those would break the comparisons that keep the list sorted. A bad line prints a warning and the driver moves on to the next one. After checking, it calls the matching method and prints the result, and it catches the ValueError that median and sum_middle_three can raise so that an empty or short list produces a warning instead of a crash. When all the lines have been read, it prints the final list.

Several decisions I made affect memory and running time. Using a doubly linked list costs one extra reference per node compared with a singly linked list, but it lets me remove a node as soon as I find it, without having to track the node behind it, and it gives me a tail reference to attach to. Storing the size costs one integer that I must keep up to date in add and delete, but it means sum_middle_three and median know the length right away instead of counting through the list. The recursive methods exists, count, total, print_list, and the search inside delete each use stack space proportional to how many nodes they pass through, so they use up to O(n) memory, where an iterative version would use constant memory. The trade-off is that Python's default recursion limit of about 1000 means these methods would fail on a list of roughly that size.

For time, add, delete, exists, count, total, sum_middle_three, and median are all O(n) in the worst case. The sorted order helps exists, count, and delete stop early once they have gone past the target value, but the worst case does not improve. Each of these recursive methods has to be a public method that starts a private helper at the head, because recursion needs a parameter that changes on each call, and the public methods do not take a node. One thing I did not optimize is add, which always starts from the head, so inserting values in ascending order costs O(n) each time. A faster version could check the tail first and attach there immediately when the new value is at least as large. The print_list method also builds its string by repeated concatenation, which copies characters more than necessary on long lists, though the recursion limit keeps lists short enough in practice that it doesn't matter.

Finally, I made sure the edge cases work. An empty list has a total of zero, prints "(empty)", and raises ValueError for median and sum_middle_three. A list with fewer than three nodes raises ValueError for sum_middle_three. Duplicates are allowed and are kept next to each other.
