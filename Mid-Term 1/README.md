Problem 1:

The key observation is that A is a prefix-sum array, so it already stores running totals. The snowfall on days i, i+1, and i+2 is the total through day i+2 minus the total through day i-1.

Any range sum becomes a single subtraction, so I never re-add daily snowfall. My first instinct was to add A[i-2] + A[i-1] + A[i], but that adds three running totals, which doesn’t represent three days of snow. For the example [6, 13, 13, 17], days 2-4 had 7 + 0 + 4 = 11 inches, and A[4] - A[1] = 17 - 6 = 11, while adding three entries gives 43. Again, the key is understanding that the values are cumulative.

The main idea behind my program is to slide a three-day window across the array of values until we arrive at the end of the array. For each window, compute A[i+2] - A[i-1] and compare it to half the total. The output is YES at the first window that qualifies, and NO if none do.

The first trap is the first window and A[0]. The formula needs A[i-1], and for the first window (i = 1) that is A[0], the total before day 1, which is 0. The input array doesn’t contain it though. With 0-indexed code, writing A[j-3] for the first window evaluates to A[-1], which is the last element of the list, meaning the grand total.

I avoided this by prepending a 0 to the list. Now A[0] = 0 and A[1…n] match the problem’s 1-indexed notation, so the formula A[i+2] - A[i-1] works for every window with no special case and no negative indexing.

The next trap is that the problem requires strictly more than half, so a window that is exactly half the total does not count. Sample input 3 tests this. Its total is 32, and the best window (days 2-4) has 5 + 6 + 5 = 16, exactly half, so the correct answer is NO. Using >= would wrongly output YES.

I also avoided floats strategically. Instead of comparing the window to total / 2, I compare 2 * window > total. Both sides are integers, so the comparison is exact, with no rounding concerns and no float conversion.

The next trap I believe is the bounds of the program. When n < 3, the answer is NO, and the code checks this explicitly instead of relying on the loop happening to do nothing. With the prepended 0, the window start i runs from 1 to n-2, written range(1, n - 1). The largest index accessed is A[i+2] = A[n], the last valid element, so the loop never goes out of bounds. When n = 3, exactly one window is checked (days 1-3), and the loop handles it correctly.

In terms of memory, after the prepend, the total is A[n]. I store it once in a variable instead of recomputing it each iteration.

The algorithm is O(n). Building the list is O(n), and the loop checks at most n-2 windows, each in constant time because of the subtraction. Without the prefix-sum insight, summing each window’s days separately would still be O(n) for a fixed window size of 3, but it would require first converting the cumulative array into daily values. Using the prefix sums directly avoids that extra step and generalizes to any window size without extra cost per window. A single pass is also optimal in the worst case, because if the answer is NO every window has to be examined.

The function returns True as soon as one window qualifies, so YES cases often finish before reaching the end of the array. The program stores the input array in O(n) space. Prepending the 0 with [0] + A creates a new list, so there is a temporary second copy of the array, which is still O(n) overall. I accepted this because it removes the special case for the first window and makes the code simpler and less error-prone, and the cost is negligible at these input sizes. If memory were critical, I could avoid the copy by computing the “before” value with a conditional (0 if i == 0 else A[i-1]) and keeping the original list, or by only keeping the last few values while reading the input. For this problem, I chose clarity over saving a constant factor of memory.


Problem 2:

The heart of my algorithm is the observation that only the counties infected most recently can cause anything new to happen. A county that was infected several days ago has already affected its neighbors, and nothing about it will change again. I call the set of recently infected counties the frontier, and instead of rescanning the entire board every day, my program only follows the frontier. These are the edges of the infection as it spreads. 

My first idea was to scan every cell each day, count its infected neighbors, and infect it if the count was at least two. That works, but each day costs O(N²) because every cell checks four neighbors, and the number of days the infection can take grows with the size of the board. So the total time can be much worse than O(N²), and rescanning cells that have not changed is wasted work. The frontier approach removes that waste. Each county is infected at most once, and when it is infected it touches only its four neighbors, so the total work for the whole simulation is O(N²), no matter how many days the infection lasts.

The data structure that makes this work is a queue. A queue is a first-in/first-out structure. In my program, the queue holds the counties that have become infected but have not yet told their neighbors. I dequeue a county, look at each of its four neighbors, and add one to a count of infected neighbors for each healthy neighbor. The first time a neighbor’s count reaches exactly two, that neighbor becomes infected and I enqueue it at the back of the line, where it waits until its own turn to spread the infection. Because the queue is first-in, first-out, the counties infected on one day are always processed before the counties infected on a later day, so the days stay in the right order.

The queue also solves the main trap in this problem which is the simultaneous update. If a county could be infected in the middle of a day and immediately count as an infected neighbor for other counties on that same day, the infection would spread faster than the rules allow. I avoid this by processing only the counties that were in the queue when the day began. At the start of each day I use for _ in range(len(queue)). The value of len(queue) is evaluated once, before the loop starts, so it fixes exactly how many counties belong to today’s frontier. Any county enqueued during the day lands behind them in the line and has to wait until the next day. This gives me simultaneous updates without copying the grid every day, which would have cost O(N²) extra memory per day.

I used collections.deque for the queue instead of a plain Python list. Removing the first element of a list with pop(0) is O(n), because every remaining element has to shift over by one position. A deque is built for working at both ends, and popleft() takes constant time. With a list, the cost of dequeueing could have undone the efficiency I gained from the frontier idea.

There were several other traps that I had to handle. The first was double-counting. A county’s infected neighbor count can go to two, then three, then four, and if I enqueued it every time the count was at least two, the same county would be enqueued several times. I avoid this by enqueueing only when the count reaches exactly two, and by marking the county as infected at that same moment. After that, the check not infected[nr][nc] skips it, so it cannot be counted or enqueued again. The second was the edges and corners of the board. A neighbor such as row -1 would not raise an error in Python, because negative indexing would silently wrap around to the last row and give a wrong answer, which is the same kind of danger I faced with A[-1] in Problem 1. I prevent this with the explicit check 0 <= nr < N and 0 <= nc < N before touching any neighbor. The third was deciding whether healthy counties remain. Instead of scanning the whole grid again at the end, I keep a running counter, infected_total, which starts at the number of initially infected counties and increases by one each time a county is infected. At the end, healthy counties remain exactly when infected_total < N * N. The same counter lets the loop stop early if the entire board becomes infected.

The loop itself ends when the queue is empty, which means no new county was infected that day and the infection has stopped spreading, or when every county is infected. Because the grid is marked as infected at the moment a county is enqueued, the printed board for each day must be shown after that day’s processing finishes, so it reflects the end of the day.

In terms of efficiency, the algorithm runs in O(N²) time, because each of the N² counties is enqueued at most once and each dequeue examines at most four neighbors. It uses O(N²) memory for the infected grid and the count grid, plus the queue, which holds only the current frontier and is never larger than the number of counties. I chose to keep a separate count grid for clarity, since it makes the rule “at least two infected neighbors” easy to read and check. It would be possible to save memory by recounting a cell’s infected neighbors each time instead, but that would trade a small memory saving for extra work and more complicated code. Printing the board costs O(N²) per day, so if the infection lasts many days, the printing adds to the total running time. The printing is an optional feature in the assignment, and the simulation itself stays O(N²).

Finally, I assume the input is well formed, so each infected coordinate appears only once and lies inside the grid. My running counter depends on this, since a repeated coordinate would be counted twice.
