Problem 2: 

For this problem, my approach was to find the highest value in the array. If the value is greater than T, the answer is 1. If not, add on the second greatest value in the array. If that sum is greater than T, the answer is 2. If not, add on the third greatest value in the array. This process continues until the sum of the values in the array is greater than T. We are given that the total sum of all values in the array is greater than T so we will always have an answer. There is no need to take into consideration an edge case where we do not find an answer.

When reading the standard input, I assigned the contents of the text file to a list called data. data used any white space as the separator. The first element in data is converted into an integer and assigned to the variable n (the number of elements in the array). The second element in data is converted into an integer and assigned to variable T (target value). I created a list called arr and added in the third element to the element at index 2+n. The 2+n helps to handle any cases in which there are extra characters in the file that we do not need. It ensures that only n elements are added into the array.

A simple for loop is utilized to iterate through the sorted version of the array, along with two counter variables. Using a sorted version keeps the original array in tact. The first counter is total, that keeps track of the sum of the elements in the sorted arr as we iterate through the array. The second counter keeps track of the number of elements that are summed together as we iterate through the sorted array.

The sorting of the array is the determining factor of the run time for the program, which is O(n log n). 


Problem 3: 

The core idea is to stop looking at triangles as three points and instead count them by the corner where the right angle sits. Every right triangle has exactly one right angle, so if I go through each point P and count how many right triangles have their right angle at P, I count each triangle exactly once and never have to remove duplicates. This removes the double-counting problem you’d get from anchoring on pairs of points.

The next question is how to count right triangles at a fixed P. A right angle at P means the segments from P to the other two vertices are perpendicular. So for a given P, I need the number of pairs of other points, let's say Q and R, such that the line from P to Q is perpendicular to the line from P to R. The brute-force version checks every pair of other points with a dot product, which costs about n² per vertex and about n³ overall. My version avoids looking at pairs at all.

For each point P, I compute the vector from P to every other point Q, which is (dx, dy). Perpendicularity depends only on which line through P the point lies on, not on how far away it is or which side of P it falls. So I want every point on the same line through P to land in the same bucket. To do that, I divide dx and dy by their greatest common divisor, which shrinks the vector to its simplest form, so (6, 8) and (3, 4) both become (3, 4). Then I fix the sign so that dx is positive, or dx is zero and dy is positive. That makes (3, 4) and (-3, -4), which point in opposite directions along the same line, map to the same key. I store these keys in a dictionary, where each key holds the number of points sitting on that line through P. This normalization is the heart of my algorithm, and it replaces slopes with exact integer pairs.

If a line has direction (dx, dy), the perpendicular line has direction (-dy, dx), which I normalize the same way. Every point in the first bucket forms a right angle at P with every point in the perpendicular bucket. So if one bucket holds c1 points and its perpendicular bucket holds c2 points, there are c1 times c2 right triangles with the right angle at P from that pair of lines. Two points in the same bucket never form a right angle with each other, because they are collinear with P, and a direction is never perpendicular to itself.

I loop over every bucket and add count times the count of its perpendicular bucket, using zero when the perpendicular bucket doesn’t exist. This visits each pair of perpendicular lines exactly twice, once starting from each of the two lines, so the sum for that vertex is exactly double the true count. Dividing by 2 corrects this, and the division is always exact because the sum is always even. Adding the results over all n points gives the final answer.

I avoided slopes and square roots. A slope needs a division, which breaks for vertical lines and introduces floating-point rounding. Tiny rounding errors make true perpendicular pairs look unequal. The gcd-normalized integer pairs are exact, so two points are on the same line through P only if their keys are identical.

The outer loop runs n times. And for each P, the first inner loop makes n minus 1 passes, and each pass computes a gcd, which takes time proportional to the logarithm of the coordinate size, log C. The second loop over the dictionary has at most n minus 1 buckets and also does one gcd per bucket. So each vertex costs about n log C, and the whole algorithm costs O(n² log C). The dictionary helps optimize the run time. It turns a pairwise comparison into a lookup, so each vertex costs roughly linear time instead of quadratic.

The dictionary is created fresh for each vertex and then thrown away, so the extra memory at any moment is at most one bucket per other point, which is O(n). The points list is another O(n). I never store the triangles, the pairs, or any table of all vertices, only running counts, so the total memory stays linear in n. A hash map spends a little memory to buy a large reduction in time, but because it is reused per vertex, the memory cost stays small.
