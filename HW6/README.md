Problem 1: Priority Queue

For this problem, the main idea is that I never put all the sales in the queue. Each log is already sorted, so the next sale overall has to be the front sale of one of the registers. I start by pushing the first sale from every register that has one, so the queue holds at most one entry per register. Then I repeat the same step until the queue is empty. I pop the smallest entry, add it to the output, and push the next sale from that same register if there is one. Since every pop is followed by at most one push from the register that was just popped, the queue can never go over k entries.

The entries I push are (time, register) tuples. I use tuples because Python compares tuples from left to right, so if two sales have the same time, the lower register number is smaller and comes out first. That handles the tie rule without extra code, and the popped entry is already in the (time, register) format. Because I only keep the register number in the queue, I use a small list called nxt that remembers which position each register’s log is up to. One thing to watch for is that a register number can only be in the queue once, so two entries in the queue never tie on both time and register.

There were some special cases that I had to consider while writing the code. Empty logs like [] must never be pushed because there is no front sale to look at, blank lines in the input need to be skipped when reading, and duplicate times across registers need the tie rule above. I also had to avoid loading every sale into the queue at the start, since that would break the size rule. For time, each of the N sales is pushed once and popped once, and each push or pop on a queue of size at most k costs O(log k), so the total is O(N log k). For memory, the queue and the nxt list are both O(k), not counting the input and the output list.


Problem 2:

For this problem I built a binary min-heap out of linked nodes. The heap object keeps a reference to the root and a count of how many values it holds. The heart of the whole solution is how I reach a spot in the tree in O(log n) time. I number the positions 1, 2, 3 and so on in level order, so position 1 is the root, 2 and 3 are its children, and so on. The binary digits after the leading 1 are the path from the root, where 0 means go left and 1 means go right. In my method _node_at(pos), I use bin(pos)[3:] to cut off the “0b1” at the front and then loop over the remaining characters, moving left or right at each one. The parent of any position is pos // 2, because dropping the last bit of the path gives the parent’s path, and the last bit tells me whether the new node is a left child (0) or a right child (1).

insert attaches a new node at position size + 1 and then sifts it up, swapping with its parent only while the new value is strictly smaller than the parent’s. Using strictly smaller means equal values stay where they are. extract_min saves the root’s value, removes the last node in the tree, copies that last value into the root, and sifts down. Sifting down compares the node with both children and swaps with whichever one is smaller, repeating until neither child is smaller. If the heap has only one node, removing the last node empties the heap, so I skip the copy and the sift in that case. peek and extract_min both raise an IndexError when the heap is empty, and is_empty and len just use the size count.

delete(value) is the trickiest method. First I search for a node holding the value. Because of heap order, if a node’s value is already bigger than the one I want, nothing in its subtree can match, so I skip that whole subtree. This search is recursive and uses "or" to return the result from the left side if it found something and the right side if it did not, which works because a Node object counts as true and None counts as false. Once I find the node, I remove the last node in the tree and put its value into the found node. That moved value could be too big or too small for its new spot, so I run both a sift up and a sift down. Only one of them will actually do anything, but I don’t have to figure out which. The trap here is when the node I’m deleting is itself the last node. In that case I just remove it and do not copy anything, because there is nothing left to fix. If I forgot that case, I would end up putting a value into a node that was already cut off from the tree. delete returns True if it removed something and False if the value was not found.

One decision I made was that sifting swaps the values between nodes instead of relinking the nodes themselves. If I had moved the nodes, I would have had to fix the parent, left, and right references on up to three nodes at every swap, and it would have been easy to leave a pointer wrong. Swapping the values keeps the shape of the tree and every reference exactly the same. Another decision was a small method called _before(a, b) that answers whether a belongs above b. In the min-heap it returns a < b, and the sift methods and the search use it instead of writing < directly. This does not change how Problem 2 behaves, but it lets Problem 3 flip the comparison in a subclass to get a max-heap without copying or rewriting any code.

build(values) throws away whatever was in the heap, attaches a node for every value in order to make a complete shape without caring about heap order, and then heapifies from the bottom up. The heapify is recursive and post-order, which means it fixes both children’s subtrees first and then sifts down the current node, so by the time a node is sifted, everything below it is already a valid heap. The sifting work adds up to O(n) because most nodes are near the bottom and barely move.

heap_sort returns the values in increasing order without changing the heap. To do that I read the values out in level order, build a temporary second heap from them, and call extract_min on that copy until it is empty, so the original heap is never touched. That is O(n log n) time and O(n) extra memory. print_heap draws the tree on a grid of characters. I find the number of levels with size.bit_length(), and a node at depth d puts its children 2 ** (H - 1 - d) columns to each side, multiplied by the width of the longest value so that bigger numbers do not run together. The / or \ goes halfway between a parent and its child on the row between them. I use a double backslash in the code because a single backslash would be treated as an escape character in a Python string. Each row of the grid is stripped of trailing spaces before printing.

For time, peek, is_empty, and len are O(1). insert and extract_min are O(log n), because walking to a position takes about log n steps and the sift only follows one path. delete is O(n) in the worst case because the search may have to look at every node, although the sifting part is only O(log n). build is O(n log n) as described above, and heap_sort is O(n log n). For memory, the heap uses O(n) for the nodes. heap_sort needs another O(n) for its temporary copy, and print_heap builds a temporary grid, which only exists while it prints and is wider than the number of values because it leaves room for a full bottom level.

Some of the traps I ran into or had to watch for were deleting the last node, removing the only node in the heap so the root has to become empty, keeping the size count correct after every attach and remove, making sure a detached node does not leave a stale child reference in its parent, handling duplicates by using strict comparisons when sifting up, and raising IndexError on an empty heap instead of crashing on a missing root.


Problem 3:

For this problem I find the median after every sale by splitting the sales so far into two halves, each kept in one of my heaps from Problem 2. The lower half goes in a max-heap called lo, so its top is the largest of the small values, and the upper half goes in a min-heap called hi, so its top is the smallest of the big values. The two tops sit right next to the middle of the data, which is why I never need to sort anything. To get the max-heap I wrote a small class, MaxHeap, that extends my MinHeap from Problem 2 and only overrides the _before method so the comparison is flipped. That means I extended my heap and did not replace it. One thing that might look odd is that on the MaxHeap, the method extract_min is the one that removes the largest value, since the method name is unchanged but the ordering is reversed.

For the median to be available in O(1) time after each sale, two things have to stay true. First, every value in lo has to be less than or equal to every value in hi, so the lower half really is the lower half. Second, the sizes have to stay balanced, meaning lo and hi hold the same number of values, or lo holds exactly one more than hi. When both are true, the middle of the data is always at the tops of the heaps. If lo has one extra value, the number of sales is odd and the median is the top of lo. If the sizes are equal, the number of sales is even and the median is the average of the two tops. Reading a top with peek is O(1), so the median is too.

To keep those two rules true, each new sale x goes through the same steps. If lo is empty or x is less than or equal to the top of lo, it goes into lo, and otherwise it goes into hi. Then I fix the sizes. If lo is two bigger than hi, I take the top off lo and put it in hi. If hi is bigger than lo, I take the top off hi and put it in lo. A single insert can only throw the sizes off by one, so one move is always enough. Moving a top value across also keeps the first rule true, because the top of lo is the biggest low value and the top of hi is the smallest high value, so whichever one crosses over still fits on its new side. After that I add the median to the output list. When the count is odd I use float() so the answer prints as 5.0 and not 5, and when it is even I divide the sum of the two tops by 2, which gives results like 4.5.

I worked through the example [5, 15, 2, 4, 8] by hand to check it. The 5 goes into lo. The 15 is bigger than 5, so it goes into hi. The 2 goes into lo, then the 4 goes into lo, making lo too big, so its top (5) moves to hi. Then the 8 goes into hi, making hi too big, so its top (5) moves back to lo. The medians are 5.0, 10.0, 5.0, 4.5, and 5.0, which matches the assignment.

The traps I watched for were using less than or equal to when comparing with the top of lo, so equal values always go to the same side and the first rule never breaks, fixing the sizes after every sale and not just some of them, and making sure both heaps have a value before reading their tops, which is safe because after the first sale lo always has at least one value and the even case only happens when both heaps are the same size and not empty. I also handled an empty list, which prints [] because the loop never runs, and an empty input, which is treated the same way. For time, each sale costs a constant number of inserts and extracts, each O(log n), so the whole run is O(n log n) for n sales, and each median lookup is O(1). For memory, every sale is stored once in one of the two heaps, so it is O(n). I never sort the sales, never keep them in a sorted list, and never use heapq, the statistics module, or any other library sorting or median code.
