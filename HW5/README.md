Problem 1: Binary Search Tree

For this problem I built a binary search tree using two classes. The first is a Node class, which just holds a value and links to a left child and a right child. The second is a BST class that holds the root and has the four required methods: add_node, delete_node, find_node and print_tree. The rule that the whole tree depends on is that smaller values go to the left and larger values go to the right, and every method takes advantage of that rule so it only has to walk down a single path instead of looking at every node. Because of this, each operation takes time proportional to the height of the tree, which is about O(log n) for the random data in this assignment, and the tree needs only O(n) memory for the nodes themselves. The worst case would be O(n) if the numbers were inserted already sorted, since the tree would turn into a linked list.

One important decision I made early on was how to treat duplicate numbers. A binary search tree needs a rule for this, and there are several common choices, such as sending equal values to the left, sending them to the right, or storing a count on each node. I decided that every value in my tree is unique, which is also how many textbooks define a binary search tree. This keeps the rest of the code simple and unambiguous, because find_node and delete_node never have to decide which of several equal copies to find or remove. To make this work, I generate the starting set with random.sample, which guarantees unique numbers between 1 and 1000 with no repeats. For the values added later, I let add_node check for a duplicate itself. If the value is already in the tree, it leaves the tree unchanged, returns False, and the demo prints a message saying nothing was added. Since the added numbers are drawn at random from 1 to 1000, a duplicate is unlikely to come up in any single run, but the guard means the tree stays correct even if one does.

The most interesting part of the code is delete_node, because there are three different situations. If the node is a leaf, or has only one child, I simply return the child (or nothing) to the parent, which cuts the node out of the tree. If the node has two children, I cannot just remove it, so I find the in-order successor, which is the smallest value in the right subtree, copy that value into the node I am deleting, and then delete the successor from the right subtree. That works because the successor never has a left child, so its removal always falls into one of the easy cases. I wrote add_node and delete_node recursively so that each call returns the new root of its subtree, and the parent reassigns its link to whatever comes back. This means I never have to track a parent pointer or write a special case for deleting the root of the whole tree. find_node is written as a plain loop instead of recursion, since it never needs to go back up the tree, and that saves the extra memory a recursive call stack would use.

A few other decisions came from traps I ran into. Deleting a value that is not in the tree prints a message instead of crashing. In the demo, I always delete the current root first, which forces one of the hardest cases to run, and then delete a few other random nodes and one value that is not in the tree. For the find section, a random number from 1 to 1000 will almost always miss, so I generate three random guesses and also search for one value picked from the tree, which guarantees I show both a found and a not found case. For printing, I used a sideways view with the right subtree on top and the left on the bottom, indented by depth, because it shows the actual shape of the tree much better than a simple sorted list would. 

This problem does not require taking anything from standard input. The code includes the generation of the random integers and the tests for adding, deleting, and finding nodes. The working directory is set to the folder that holds my python file. In my terminal I simply type "python3 bst.py > bst_outputX.txt" to run the code once the working directory has been set. Each call results in a different result since it generates different numbers each time. And, it writes the result into a .txt file that will be included in my repo.

Problem 2: Morse Code with Vowels

For this problem, I used dynamic programming to count how many different ways a string of dots and dashes can be split into vowels only. The heart of the algorithm relies on what the last vowel in the decoding was. Every valid decoding of the first i symbols must end with exactly one vowel, and in Morse code every vowel is 1, 2 or 3 symbols long. E is a single dot, A and I are .- and .., and O and U are --- and ..- . So at each position I only need to look at the last one, two and three symbols. If they form a vowel, then everything before that vowel is a smaller version of the same problem, and I already know how many ways there are to decode it. The number of ways to decode the first i symbols is therefore the sum of the ways to decode the shorter pieces that leave a valid vowel on the end.

To code this, I created a list called ways, where ways[i] holds the number of ways to decode the first i symbols. I set ways[0] = 1, because there is exactly one way to decode nothing, and every other spot starts at 0. Then I loop through the positions from left to right, so every smaller answer I need has already been calculated by the time I need it. At each position, I start a running total at zero and make three checks. If the last symbol is a dot, I add ways[i - 1]. If the last two symbols are .- or .., I add ways[i - 2]. If the last three symbols are --- or ..-, I add ways[i - 3]. I then store the total in ways[i], and when the loop finishes, the last entry in the list is my answer. For input, the first line gives n and the second line gives the string, and I use .strip() so a stray space or newline at the end is never counted as a symbol. I loop over the actual length of the string instead of trusting n, so a typo in the first line can never make the program read past the end.

One piece of special code is how I get the file name to include in the output. The assignment requires the output to say which input file was used, but when I run python3 vowel.py < vowel_input1.txt, the shell opens the file for me and gives the program an anonymous stream, so Python never sees the name. To solve this, I did look up how to find the file name from a Mac specifically (which is what I use). Standard input is always file descriptor 0, and fcntl.fcntl(0, fcntl.F_GETPATH, bytes(1024)) asks the operating system for the full path of the file attached to it. I cut the result off at the first null byte, decode it into a string, and use os.path.basename to keep only the file name. This only asks a question and does not use up any of the input, so my later reads still start at the beginning of the file. The tradeoff is that F_GETPATH only exists on macOS, so the program has to be run on a Mac with the file passed in using <.

In terms of efficiency, the program makes one pass through the string and does at most three small comparisons per position, so the running time is O(n). The ways list holds one number per position, so the memory is O(n). I kept the full list because it makes the logic easy to follow and easy to check by hand, but since each position only looks back three places, I could have kept just the last three values and brought the memory down to O(1). The most important efficiency decision was using memoization. The number of decodings can get very large, so listing every one would take far too long, but because I only count them and reuse the counts for shorter pieces, every piece is solved exactly once. 

I ran into a few traps along the way. A simple left-to-right approach that grabs the first vowel it sees does not work, because the vowels overlap.  ..- can be read as the single vowel U, or as the two vowels E and A, and the table has to count both. The other trap is Python’s negative indexing. At the start of the string, looking back two or three symbols would reach for positions that do not exist, and Python would quietly wrap around to the end of the string or list instead of giving an error. I guard the two-symbol and three-symbol checks so they only run when there are enough symbols behind them. Dead ends also work out on their own: if no vowel can end at a position, nothing gets added and that spot stays at 0, but later positions can still recover by looking back past it. If a string can never be split into vowels, the answer ends up as 0.

This problem takes standard input. After setting the working directory the folder that contains the python file and the input text file, you can open the Terminal and run the command. Instead of providing screenshots, I wrote the results of each input into one .txt file using the following command:

for i in 1 2 3 4; do python3 vowel.py < vowel_input$i.txt; done > vowel_output.txt

The results of each run is stored in the .txt file vowel_output.txt

Problem 3: Longest Sequence

For this problem, I used dynamic programming to find the longest sequence that alternates between the two arrays while its values keep increasing. The heart of the algorithm is to stop thinking about the whole sequence and instead determine what the longest valid sequence would be if we ended at any given point. Similar to your explanation in class, while iterating through the possible sequences, we find that we already know what the longest sequence is at certain points. I use memoization again for this to store those values. I keep two lists, best_a and best_b. best_a[i] is the longest valid sequence that ends with a[i], and best_b[j] is the longest valid sequence that ends with b[j]. Every element can start a sequence by itself, so every spot starts at 1. After that, an element can only extend a sequence that ended in the other array, because the sequence has to alternate. So a[k] can be added to the end of a sequence that ended at some earlier position j of B, as long as b[j] is smaller than a[k], and the new length is best_b[j] + 1. The same rule works the other way for b[k]. I keep whichever extension gives the longest result, and the final answer is the largest number in either list. The sequence is allowed to start in either array, so taking the largest value across both lists covers both cases.

The part of the problem that I had to read carefully is the position rule. The example in the assignment shows that {1, 4, 7} is not valid, even though its values increase, because the 4 is in position 1 of B, and that is not after the 1 in position 1 of A. So each new element has to come from a strictly later position than the element before it, and that is why my loops only look at positions j < k, and never j <= k. This rule also let me simplify the code. Since a[k] only depends on positions of B before k, and b[k] only depends on positions of A before k, neither one needs the other’s answer at position k. I can walk through the positions once, from left to right, and fill in both lists in the same loop, and everything I need has always been calculated already. On the sample input, this finds the sequence 2, 3, 4, 6, which takes a[2], then b[4], then a[5], then b[6], and its length of 4 matches the expected output.

In the code, I read the sizes from the first two lines and the two arrays from the next two. I use the real lengths of the lists in my loops instead of trusting the given sizes, so the program cannot run off the end if a size is wrong. The loop variable k goes up to the length of the longer array, and I check k < len(a) and k < len(b) before using each one, so a shorter array simply stops taking part. The inner loops use min(k, len(b)) and min(k, len(a)) as their limits, which means they only scan earlier positions that actually exist. The last line uses max(best_a + best_b, default=0), so an empty input gives 0 instead of crashing. 

The file name is found the same way as in Problem 2. I ask macOS which file is attached to standard input with fcntl.F_GETPATH, keep only the base name with os.path.basename, and print it with the answer. This only works on a Mac, and the file has to be passed in with <.

For efficiency, each element looks back over the earlier positions of the other array, so the total work is about the length of A times the length of B, which makes the running time O(n·m). The memory is only O(n + m), because I store a single number for every element and nothing else. The program also never builds the sequence itself, only its length, which saves time and memory since the assignment only asks for the length.

This problem takes standard input. After setting the working directory the folder that contains the python file and the input text file, you can open the Terminal and run the command. Instead of providing screenshots, I wrote the results of each input into one .txt file using the following command:

for i in 1 2 3 4 5 6; do python3 longest_seq.py < longest_seq$i.txt; done > longest_output.txt

The results of each run is stored in the .txt file longest_output.txt
